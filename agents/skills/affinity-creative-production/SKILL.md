# AFFINITY Creative Production Skill

Version: 2.0
Status: Canonical creative execution skill for GrowthOps
Last updated: 2026-09-07

## Mission
Create and continuously improve high-converting public pages, posts, articles, comparison experiences and creative marketing assets by combining the canonical `skills/AFFINITY_SKILL.md` funnel/conversion framework with a modern, performance-first web-design and page-generation system.

This skill is execution guidance for GrowthOps. It does not select products, invent demand, replace SocialMarket canonical market intelligence or create an independent schedule.

## Mandatory dependencies
Always load/apply, as relevant:

1. `skills/AFFINITY_SKILL.md` — commercial truth, product gates, Greece/EU economics, tracking, funnel authority.
2. `skills/AFFINITY_PAGE_ENGINE.md` — PagePilot/Magnetic-derived page-generation workflow, angle/message-match logic, Page DNA, modular generation, rapid variants.

## Mandatory page-generation protocol
For new or materially rebuilt pages, execute:

`SOURCE INGEST → CONTEXT BRIEF → ANGLE MATRIX → MESSAGE MATCH → ARCHETYPE → PAGE DNA → COMPONENT PLAN → COPY → MEDIA → DESIGN TOKENS → ASSEMBLY → RESPONSIVE QA → CONVERSION LAYER → LOCALIZATION → VARIANTS → PUBLISH → MEASURE`

Do not jump from raw product URL or user prompt directly to HTML/React.

### 1. Source ingest
Collect product/merchant/competitor URL information, campaign copy, brand context, user files and AFFINITY evidence.

### 2. Context brief
Normalize into audience, pain, desire, offer, quick win, mechanism, objections, verified claims and target action.

### 3. Angle matrix
Generate and score evidence-backed angles; select the highest-fit angle rather than the most dramatic.

### 4. Message match
If traffic comes from an ad/email/social/campaign, continue the exact problem/promise/offer that earned the click.

### 5. Archetype
Choose product, comparison, high-ticket, pain-gap, checklist, playbook, resource-list, personalized follow-up, etc. before choosing components.

### 6. Page DNA
Create a valid Page DNA object conforming to `PAGE_DNA.schema.json` whenever the implementation environment supports structured specs.

### 7. Component plan
Use `COMPONENT_REGISTRY.md`. Prefer existing components. Add a custom component only when it solves a repeatable need the registry cannot express cleanly.

### 8. Copy
Generate copy to component constraints rather than writing one long undifferentiated sales document.

### 9. Media
Specify media intent separately: verified product image, product detail, lifestyle context, diagram, comparison, demo, data visualization, etc.

### 10. Design tokens
Generate one coherent page design system, not random styling per section.

### 11. Assembly + responsive behavior
Build mobile-first and define section order, stacking, crop and sticky behavior explicitly.

### 12. Conversion layer
Add trust, CTA, upsell, lead capture, FAQ, calculator, cart or affiliate destination behavior only when justified.

### 13. Localization
Rewrite for target market; do not literal-translate direct-response copy.

### 14. Variants
Create controlled variants by locking stable facts/design and changing one material hypothesis at a time.

### 15. Publish + measure
Instrument and return the deployment/export and experiment state.

## Message-match policy
A campaign page must answer "Am I in the right place?" immediately.

Capture when available:
- source hook
- source problem
- source promise
- source offer
- source visual theme
- source CTA expectation.

The page hero and first proof sequence must continue these signals. If materially different audience/angle/offer variants are needed, create separate controlled page variants rather than merging contradictory messages into one hero.

## Component intelligence policy
Every substantial section should map to a component ID from `COMPONENT_REGISTRY.md` or a justified new component with:
- role
- conversion goal
- best-for conditions
- avoid-when conditions
- required inputs
- evidence requirements
- copy limits
- media requirements
- mobile behavior
- accessibility requirements
- analytics events
- fallbacks.

Do not call a component “high converting” universally. Learn conditional performance by product, traffic, audience, archetype and offer.

## Page strategy
The shortest honest persuasive path wins. Select structure from AFFINITY funnel analysis. Typical flow may include:
1. buyer problem/outcome
2. high-signal evidence or quantified context
3. why current/local alternatives leave a gap
4. product/solution mechanism
5. proof/specifications/comparison
6. economics/ROI when defensible
7. trust: warranty, returns, delivery, support, installation burden
8. clear CTA through verified affiliate/tracking URL.

Do not add sections, popups, animations, calculators or interaction merely to appear premium.

## Lead-magnet / Magnetic-style layer
For non-commerce resources, select the format first.

### Checklist
Message-matched hero → why it matters → grouped checklist → quick win → next action/download.

### Playbook
Outcome → audience/context → steps → examples/templates → mistakes/risks → next action.

### Mini-guide
Promise → summary → concise chapters → examples/visuals → action summary → CTA.

### Resource list
Purpose → categories → resource cards → why/when to use → CTA.

### Personalized sales follow-up
Prospect/account-specific hero → relevant context → problem/opportunity → tailored insight/resource → proof → low-friction meeting/contact CTA.

### Link-in-bio
Identity/context → primary current resource/offer → grouped links → real proof if useful → newsletter/contact CTA.

## Rapid variants / remix rule
Do not random-regenerate complete pages for testing.

Lock stable layers:
- verified facts
- compliance/trust facts
- product media where exact fidelity is required
- design tokens when visual identity is not the hypothesis
- most section structure.

Change controlled layers:
- audience
- angle
- hero proposition
- proof order
- economic framing
- CTA copy
- hero visual.

Store parent/variant relationship and experiment hypothesis.

## Web design framework policy
Choose the smallest high-quality implementation stack that matches the existing project and deployment adapter.

Preferred patterns:
- Existing Next.js/React project: Next.js App Router + TypeScript where already used; Tailwind CSS when project-standard; shadcn/ui or Radix primitives for accessible UI patterns when compatible.
- Content-heavy/mostly static public experience where a new stack is actually warranted: Astro or static semantic HTML/CSS with minimal JavaScript, subject to the existing deployment architecture.
- Existing vanilla microsite: semantic HTML + modern CSS + minimal JS; do not rewrite to React only for fashion.
- Shopify commerce: respect theme/template/section architecture and existing integrations; avoid unnecessary replacement of native commerce behavior.
- Existing Webflow/Lovable/ChatGPT/other builder: preserve native design-system primitives and use the platform adapter rather than recreating the site elsewhere.

Motion:
- Prefer CSS transitions or native platform motion for small effects.
- Framer Motion in React only where it materially improves comprehension or interaction.
- GSAP only for justified high-value storytelling/animation and only when performance budget permits.
- Avoid animation that delays CTA comprehension or worsens Core Web Vitals.

## Design quality standard
Every page must be:
- mobile-first and responsive
- visually distinctive for the actual product/audience, not a repeated house template
- fast and lightweight
- accessible by keyboard and screen reader where interactive
- high-contrast and readable
- clear in hierarchy and scanning behavior
- conversion-focused without deceptive dark patterns
- trustworthy near conversion points
- consistent in spacing, typography and component behavior
- robust at common mobile widths and large desktop widths.

Use a deliberate design system per experience:
- typography scale
- spacing scale
- grid/container rules
- radius/border/shadow rules
- iconography rule
- CTA hierarchy
- motion rule
- responsive breakpoints
- reusable component tokens.

Minimum token coverage should include PagePilot-style configurable concepts:
- heading/body sizing
- heading/body colors
- brand color
- CTA background/text
- corner rounding
- CTA behavior
- per-device spacing/order/visibility.

AFFINITY extends this with container/grid, line-length, surface/elevation, focus state, image crop and motion-budget rules.

Do not use random visual treatments section by section.

## Art direction
Art direction is derived from the market/product/use case. Examples: premium editorial, industrial precision, technical utility, B2B procurement, Mediterranean lifestyle, hospitality, automotive diagnostic, home-efficiency, travel, etc.

Do not mechanically reuse one hero style, gradient, card layout or color identity across unrelated sites.

## Media / image production
For every major visual define:
- objective
- subject
- use context
- source/provenance
- required product fidelity
- aspect ratio
- mobile crop
- whether text overlay is allowed.

Useful asset types:
- verified product hero
- detail/spec image
- lifestyle/use-case context
- in-hand/in-use image
- studio product image
- mechanism diagram
- comparison graphic
- step/how-it-works image
- short demo video
- GIF where useful
- infographic/data visualization
- social creative.

When generating product visuals:
- prefer clear source images with the whole product visible
- avoid source watermarks/text/logos when possible
- prompt for the actual niche/audience/use context
- generate controlled visual variants for testing.

AI-generated visuals must not misrepresent the real product's shape, controls, accessories, dimensions, configuration or results. For exact product representation, prefer verified merchant/manufacturer imagery or use supplied product imagery as reference.

## Creative marketing assets
For each asset, define:
- objective
- audience/use case
- single dominant message
- angle ID
- verified product/market claim set
- visual concept
- composition/layout
- product prominence
- CTA or next action
- dimensions/channel variants
- text-safe zones
- accessibility/readability constraints
- source/provenance for product media.

Creative must be generated from real product/evidence inputs. Never invent testimonials, customer counts, ratings, awards, scarcity, medical/scientific claims, discounts or before/after performance.

## Ad-to-page continuity
When ad creative/copy is generated together with a landing page, the ad and page must share:
- audience
- angle ID
- core problem/promise
- offer
- visual story
- CTA expectation.

Generate several ad variations around one angle rather than mixing unrelated angles into one page.

## Copy standard
Follow AFFINITY copy hierarchy:
Outcome/problem -> defensible context -> mechanism -> evidence -> economic comparison -> risk reduction -> CTA.

Writing rules:
- human, specific, concise
- avoid generic AI filler
- match buyer sophistication and purchase mode
- state disadvantages/material limitations when relevant
- use Greek or English according to target market/search intent
- preserve claim/evidence classes internally
- affiliate disclosure must be clear but should not dominate the buyer experience.

Generate copy **per component**. Typical constraints:
- hero eyebrow: 2–6 words
- hero headline: 5–12 words
- hero support: 18–40 words
- CTA: 2–5 words
- benefit title: 2–6 words
- benefit body: 12–30 words
- FAQ answer: usually 25–90 words.

If content exceeds the component's capacity, edit the content or change the component; do not shrink typography into unreadability.

## Localization
Localization is native rewriting, not literal translation.

For Greece-facing pages:
- natural Greek
- EUR
- Greece delivery/warranty/returns context
- local comparator context where relevant
- local buyer terminology
- responsive reflow for longer Greek copy.

Preserve facts, persuasion structure, brand voice and evidence status.

## SEO page/post production
For articles and posts:
- target validated search intent, not arbitrary keyword stuffing
- satisfy the query first; commercial CTA second
- use semantic headings and strong information architecture
- add internal links only when topically useful
- use FAQ/schema only when content actually supports it
- use original synthesis/evidence; do not mass-produce near-duplicate pages
- align title/meta/intro with actual page promise
- create comparison tables only with honest comparable dimensions
- maintain crawlability, canonical and sitemap integration
- avoid supplier/competitor duplicate copy.

## Conversion instrumentation
Every new or materially changed commercial page must expose the agreed GrowthOps events when supported:
- pageview
- session_start
- qualified_view where defined
- CTA exposure/click where instrumented
- affiliate_click
- calculator/quiz completion when present
- lead/key_event/purchase when reliably available
- share event where useful.

For component learning, capture component IDs/exposure where technically and legally appropriate.

The page must have a defined primary conversion metric and baseline/measurement window when launched as an experiment.

## Experimentation hierarchy
Prioritize tests in this order:
1. product/offer
2. audience/use case
3. angle/message match
4. hero proposition
5. economic framing
6. proof type/order
7. CTA placement/copy
8. component sequence
9. hero/media treatment
10. styling details.

Avoid confounded experiments that change many unrelated variables at once.

## Performance budget
Default goals unless the existing project imposes stricter limits:
- minimize blocking JavaScript
- responsive optimized images
- lazy-load noncritical media
- no oversized hero video by default
- avoid unnecessary third-party scripts
- preserve or improve Core Web Vitals
- no visual library added for one trivial component.

A design enhancement that materially degrades performance requires explicit evidence that the tradeoff is worthwhile; otherwise reject it.

## QA gates before production
PASS only when applicable checks succeed:
- source facts reconciled with AFFINITY evidence
- explicit selected angle
- message-match defined when campaign-driven
- page archetype named
- Page DNA produced for new/materially rebuilt pages when supported
- every major section maps to a registry component or justified custom component
- page/build renders without error
- mobile and desktop layout reviewed
- no horizontal overflow
- CTA and affiliate destination correct
- tracking URL remains verified
- no unsupported or deceptive claims
- no fake urgency/scarcity/reviews/ratings/percentages
- metadata/canonical/schema valid
- image/media provenance acceptable
- product representation accurate
- links work
- accessibility basics pass
- Core Web Vitals/performance not materially regressed
- analytics events fire as designed
- no duplicate/conflicting conversion tracking.

Recommended Page Engine QA score: >=85/100 with no hard failures in claim integrity, destination, tracking, product-media accuracy or mobile usability.

## Monthly optimization
During the existing AFFINITY monthly optimization cycle:
- review component-level and page-level performance
- update best-for/avoid-when metadata
- retire weak/noisy/deceptive patterns
- add newly verified useful public techniques from strong tools/sites
- update archetype selection rules
- refresh copy limits where measured evidence supports change
- refresh responsive/performance standards
- preserve experiment history and source provenance.

Do not create a separate schedule; participate in the existing AFFINITY/GrowthOps optimization process.

## Non-negotiable rules
- AFFINITY is the commercial/funnel design authority for affiliate experiences.
- SocialMarket demand/competition/pain truth is never replaced by creative inference.
- `AFFINITY_PAGE_ENGINE.md` is the mandatory page-generation grammar for new/material rebuilds.
- `COMPONENT_REGISTRY.md` is the default reusable component source.
- Best design means best fit + clarity + trust + performance + conversion, not maximum visual complexity.
- Never generate fake proof or deceptive urgency.
- Never expose secrets or internal commission economics to consumer pages unless specifically required.
- Never copy a competitor/vendor's proprietary code or exact design as a substitute for original implementation.
- Reuse existing project stack when sound; do not create framework churn.
- A page must be editable, remixable and measurable, not a one-off opaque code dump.
